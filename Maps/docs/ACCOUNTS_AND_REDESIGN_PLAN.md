## Context

At the start of this work, Manarah was fully anonymous and device-local: favourites, saved pins, home location, and review-verification all lived only in `localStorage`. Reviews were gated by a one-off email+OTP flow (7-day token), so a review couldn't be edited/deleted later and nothing followed a user across devices. The place-detail view was a floating MapLibre popup capped at ~320px, too small for phone/website/inline reviews. The right-side button rail had grown to 6 stacked pills with no room for account/profile UI.

This plan added Firebase Auth (Google/Microsoft sign-in, email magic link, and email/password accounts) as a pure **identity layer** — no Firestore. The original Sheets/Apps Script persistence layer has since been replaced by Cloudflare D1 (see `docs/D1_MIGRATION_PLAN.md`), which is now the source of truth for synced favourites/home location/reviews. Firebase ID tokens are verified at the Cloudflare Pages Function edge (Web Crypto + Firebase's public JWKS — no server SDK needed).

**Privacy principle (per your instruction):** no plaintext email is stored anywhere for the purpose of linking a person to their data. Every sheet row that ties a saved place, home location, review, or rating to a person stores only `emailHash = sha256(verified email)` — never the email itself. This hash is computed the same way for Firebase Google, Microsoft, magic-link, and email/password sign-in, or (for historical continuity) the legacy anonymous OTP flow, so a review written anonymously and later claimed by signing in with the same email still matches. The existing Reviews sheet's plaintext `email` column (col D, currently kept "for abuse identification") stops being populated by any new code in this plan — see Phase 6.

**Design decision flagged for your review:** signing in replaces the anonymous email-OTP flow for *new* reviews going forward (one identity system, not two). Anonymous users can still browse/favourite locally exactly as today; they just need to sign in to write a new review or sync across devices.

Apps Script (`scripts/apps-script/Code.gs`) has **no automated deploy** — every change requires manually pasting into the Apps Script web editor and clicking Deploy → New Deployment. This plan batches all `Code.gs` changes into two checkpoints (end of Phase 3, end of Phase 6) instead of one per feature, to minimize how often you need to do that.

## Phase 9.1 — Post-deploy investigation: "signed in but nothing happened" 🤖
**Status:** `[x]` Done · **Depends on:** Phase 6's deploy (now landed) · **Your action needed:** none for the fixes below; see the still-open manual bullets in Phases 7-9 for what only you can do

After the Apps Script deploy landed, you tested sign-in on the real site and reported: *"the login works, but didn't do anything with the login (e.g. review, saved pages etc)"*. Investigated end-to-end with the mocked-Firebase Playwright harness (`tests/14-auth-account.spec.js`, extended — 20 tests, all passing) rather than trusting a code read. Findings:

- **The "Your reviews" empty state was working correctly, not silently failing.** Added tests that capture the actual `POST /api/reviews` network request (not just DOM state) for both a populated and an empty `my-reviews` response — in both cases the request fires with the real `idToken` attached and the DOM renders correctly. A brand-new account with zero prior reviews correctly shows "You haven't written any reviews yet." This is accurate behavior, not a bug — but see the next finding for why it *read* as broken.
- **Real bug (now fixed): the Google sign-in button gave zero visible confirmation on success.** `src/menu.js`'s `_wireSignedOutView()` Google-popup handler had no success-path feedback at all — compare to `src/reviews.js`'s own sign-in prompt, which already calls `showToast("Signed in", "check")` on success. For a first-time sign-in with no pre-existing reviews/saved places to reveal, a successful sign-in and a silently-broken one looked identical. Fixed by adding the exact same `showToast("Signed in", "check")` call (matching this app's existing toast convention, not inventing a new one) to: (a) the interactive Google-popup success path in `menu.js`, and (b) a genuine magic-link-completion event only (`auth.js`'s `initAuth()` now returns whether a pending magic link was just completed; `menu.js` shows the toast only in that case) — an ordinary page load that merely restores an already-signed-in cached session stays silent, matching this feature's "purely additive, invisible" background-sync design. Verified both paths with dedicated tests, including a negative test proving the toast does *not* fire on an ordinary already-signed-in page load.
- **Real bug (now fixed): a race condition silently skipped the Phase 8 background sync for the magic-link sign-in path specifically.** `src/menu.js`'s `initMenuAccount()` called `await _auth.initAuth()` *before* `initAccountSync()`. `initAuth()` can synchronously complete (and dispatch `EVT.AUTH_CHANGED` for) a pending magic-link sign-in as part of its own execution — if that dispatch happens before `account-sync.js`'s `EVT.AUTH_CHANGED` listener is registered, the listener simply never sees it (a `CustomEvent` doesn't replay to late listeners), so the sign-in merge silently never ran. The interactive Google-popup path was never affected (by the time a user clicks that button, `initMenuAccount()` has long since finished running on page load, so the listener is already in place) — only a magic-link return-trip completion could hit this. Fixed by reordering: `initAccountSync()` now runs before `_auth.initAuth()`. Added a regression test that drives a real magic-link completion (via the mocked SDK's `mockSignInLink=1` URL convention) and confirms `POST /api/account` `sync-saved` actually fires — this test would have failed before the reorder.
- **The `emailHash` bridge normalization is correct — no mismatch found.** Compared `scripts/apps-script/Code.gs`'s legacy OTP path (`sha256Hex(email.trim().toLowerCase())`, `Utilities.computeDigest` with UTF-8 string input) against `functions/api/account.js` and `functions/api/reviews.js`'s Firebase path (`sha256(verified.email.trim().toLowerCase())` via Web Crypto's `TextEncoder`/`crypto.subtle.digest`). Both are trim + lowercase + UTF-8-encode + SHA-256 hex, byte-for-byte equivalent. An anonymous OTP review and a later Firebase sign-in with the same email genuinely produce the same `emailHash` — the plan's core stated privacy/continuity guarantee holds as designed.
- **No stray JS errors found** in a real headless-Chromium run (console/network inspected throughout, same rigor as the Phase 5-9 SRI-mock/`currentUser`-getter debugging) beyond the two real bugs above.

**Files touched:** `src/auth.js` (`initAuth()` now returns a boolean), `src/menu.js` (toast on Google-popup success and on genuine magic-link completion; `initAccountSync()` reordered before `initAuth()`), `tests/14-auth-account.spec.js` (10 new tests: 3 real-network-call assertions for review-submit/favourite-toggle/sync-saved/my-reviews, 1 toast-on-Google-signin test, 4 magic-link-completion tests including the race-condition regression test and its "no stray toast on an ordinary reload" negative counterpart).

**Ancillary finding, not fixed (flagging for your judgment, out of scope for this investigation):** while building the review-submission network test, found that opening the "Write a review" form for a place with **zero existing reviews** locks the overlay card at a very short height (`_insertReviewPanel`'s "reveal within the scroll area" design, so the panel doesn't visually push content around) — and the newly-revealed star-rating row can end up positioned right at that locked boundary, requiring precise scrolling within a small (~106px) internal scroll pane to fully reach the stars/submit button. This reproduced with both Playwright's synthetic click and both `scrollIntoViewIfNeeded()` and native `scrollIntoView({block:'center'})`, consistently leaving the star row ~8px clipped at the bottom of the visible window even after scrolling — a genuine layout tightness, not a test artifact (confirmed via `getBoundingClientRect()`/`elementFromPoint()` inspection, not just visual guessing). This is a plausible minor real-world friction point specifically for a place's *first* review (the most common case for a growing directory), independent of the sign-in bug this session investigated. Not fixed here since it's unrelated to what was reported and deserves its own look at the `_insertReviewPanel`/`.rv-write-panel` sizing rather than a quick patch.

**2026-08 follow-up — root cause of the above confirmed and fixed.** `_insertReviewPanel()` pinned `.rv-overlay-card`'s inline `style.height` at the pre-panel height and **never released it** — the only release path was `_restoreReviewSummary()` on form-close, or as an incidental side effect of some later, unrelated `_animateReviewCardHeight()` call. While pinned, the card could never grow past that stale pre-panel size (matching this ancillary finding exactly), and any further reveal inside the panel (e.g. the sign-in prompt's "Continue with email" step) FLIPped from that same stale baseline — see `docs/PREFERENCE_LOG.md` for the full trace. Fixed by having `_insertReviewPanel()` release its own lock (`card.style.removeProperty("height")`) once `.rv-write-panel`'s open transition ends (`transitionend` on `grid-template-rows`, with a timer fallback), so the card returns to natural max-height-capped sizing as soon as the panel settles, instead of staying artificially clipped. `src/menu.js`'s analogous `.menu-account-panel`/`_animateMenuPanelHeight` has no equivalent extra pin and was unaffected.

## Phase 9.2 — Live-testing fallout: review delete, cross-device removal, real Yes/No confirms 🤖
**Status:** `[x]` Done · **Your action needed:** the same batched `Code.gs` deploy this plan has been tracking, plus the manual spot-checks below

Three issues surfaced by your own real-device testing (Mac + iPhone, same Google account) after the Phase 5-9 deploy.

**a. Review delete was completely broken, front and back.** Root cause, confirmed by tracing every Reviews-sheet row match in `Code.gs`, not guessed: `getMyReviews()` (added in Phase 7, the function that successfully *lists* "Your reviews") was the only one of the four match functions (`handleReviewCheck`, `handleReviewSubmit`'s dedup, `handleReviewDelete`, `getMyReviews`) that defensively normalized the raw Sheets cell value via `.toString()` before comparing it. The other three used a bare strict `===` directly against `getValues()`'s raw output — fragile against anything that isn't already a clean, whitespace-free string (Sheets' own automatic type coercion of numeric-looking text, or incidental whitespace from any manual edit of the sheet). That asymmetry is exactly why the symptom looked the way it did: the review visibly exists (found by the lenient function), but delete's stricter, unnormalized comparison can silently fail to recognize "the same" row and return `not_found` — which the client correctly reports as a failure rather than lying about success. Fixed by routing every placeId/emailHash/status comparison in `handleReviewCheck`/`handleReviewSubmit` (including the `Places` sheet's own `placeExists` check)/`handleReviewDelete`/`getMyReviews` through one new `_normReviewCell()` helper, closing the entire class of drift rather than patching one call site. `src/menu.js`'s delete failure path also now shows a toast on failure (`"Couldn't delete review"`) — previously silent, which was itself a smaller, compounding UX gap on top of the real bug.

**b. Cross-device *removal* didn't propagate — a real architectural gap in the original Phase 8 scope, not a bug against it.** Phase 8 was explicitly scoped as a pure additive union that "never deletes anything on either side" (see Phase 8 above) — this is that gap being closed, not a bug fix against the original design.
  - **Before:** `_mergeFavourites`/`_mergePins`/`_mergeHome` only ever added — anything local-only got pushed up, anything server-only got adopted locally, and an item removed on one device (via its own correctly-working `_backgroundSync` unsave call) would sit forever on any *other* device that never independently re-removed it, since that other device's merge had no way to tell "genuinely new local item" apart from "previously-synced item now deleted elsewhere" — both look identical as a single local-vs-server diff.
  - **Also checked, and NOT a bug as originally hypothesized:** re-verified whether the merge only ever ran once, at initial interactive sign-in. It doesn't — Firebase's `onAuthStateChanged` callback fires once on every page load with the restored persisted session (not just on a fresh interactive sign-in), `src/auth.js`'s `initAuth()` dispatches `EVT.AUTH_CHANGED` from inside that callback, and `src/account-sync.js`'s listener for it is already registered (in `menu.js`'s `initMenuAccount()`, before `initAuth()` runs — the exact ordering the Phase 9.1 magic-link race fix already established) by the time that fires. So a device that's already signed in and simply reloaded/reopened *does* already re-run the merge on that load. The real, sole gap was (a) above — the merge running again doesn't help if it structurally can't express "remove."
  - **Fix:** `_mergeFavourites`/`_mergePins`/`_mergeHome` are now a true two-way reconcile. A new "known synced" baseline (`hf_sync_known_v1` in localStorage, `_getKnownSyncState()`/`_setKnownSyncState()`) records the local truth immediately after every successful merge. On the next merge, a local item missing from the server's list is pushed up (genuinely new, never seen before) if it's *not* in that baseline, or removed locally (synced before, now gone from the server — removed on another device) if it *is*. Order matters: push-new happens before remove-if-known, so a not-yet-uploaded local addition is never mistaken for a removal.
  - **Also made explicit, per your direction, as a belt-and-suspenders addition (not the primary fix, since (b)'s "doesn't reconcile on load" hypothesis didn't hold up under trace):** `initAccountSync()` now also calls `_syncOnSignIn()` directly whenever `auth.getCachedAccount()` is already truthy at call time, rather than relying solely on the implicit `onAuthStateChanged`-fires-`EVT.AUTH_CHANGED` timing. Harmless to call twice — `_syncOnSignIn()`'s own `_syncing` guard makes the second call (from whichever path fires second) a no-op.
  - **Residual edge case — flagged, not solved:** a local removal made while the device is genuinely offline never reaches the server, since `_backgroundSync()` is fire-and-forget with no retry/offline queue. If a reconcile-from-server pull happens on that same device before connectivity returns and the removal is ever retried, the server's still-has-it copy looks exactly like a legitimate "adopt this locally" case (nothing distinguishes it from a real cross-device addition) and can silently resurrect the item the user just removed. There is no tombstone/deletion-log in this design — this one scenario can still lose a removal. Not oversold as airtight; see `docs/PREFERENCE_LOG.md` for the same writeup.
  - [ ] 🧑 Manual test (after the `Code.gs` deploy below): remove a saved favourite/pin from one signed-in device, then simply reopen (or reload) the *other* already-signed-in device and confirm it disappears there too, without needing to re-toggle anything on that second device.

**c. Real Yes/No confirmation for review delete and account sign-out, replacing the press-twice pattern.** New `showConfirmDialog()` (`src/utils.js`) + `.confirm-overlay`/`.confirm-card` template (`design-tokens.css`) — one reusable component, built and torn down entirely in JS per call (same create-on-demand convention as `showToast()`), used for both `.acc-review-delete` (`variant: "danger"`) and `#menu-signout` (`variant: "default"`). Full writeup, including why the shell reuses `#promos-overlay`'s fixed-centered-overlay shape and why the button-pair mirrors `.menu-account-signin-row`'s equal-weight convention, in `docs/DESIGN_SYSTEM.md`. The press-twice pattern is explicitly marked obsolete there rather than silently left as a stale "current reference."

**Files modified:** `scripts/apps-script/Code.gs` (gitignored — deploy-only; `_normReviewCell()` + every Reviews-row/Places-row match updated), `src/account-sync.js` (two-way reconcile + explicit on-load reconciliation), `src/utils.js` (`showConfirmDialog()`), `src/menu.js` (review delete + sign-out now use `showConfirmDialog()`; delete failure now toasts), `src/styles/design-tokens.css` (`.confirm-overlay`/`.confirm-card`/`.confirm-icon`/etc. template), `tests/14-auth-account.spec.js` (delete/sign-out tests rewritten for the Yes/No dialog), `docs/DESIGN_SYSTEM.md`, `docs/ACCOUNTS_AND_REDESIGN_PLAN.md`, `docs/PREFERENCE_LOG.md`.
